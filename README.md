<!-- portfolio-card:end -->

Дать агенту задачу на изменение проекта и видеть, что он сделал, что проверил и где остановился. Atlant запускается локально, работает через установленный Codex CLI и показывает ход работы в терминальном интерфейсе.

Процесс разделён по обязанностям: CORE проверяет требования, ARCH определяет план и интерфейсы, CODER меняет файлы. Есть режим для существующего проекта и режим генерации по заданию.

## Работа, которую можно продолжить

Состояния и контрольные точки сохраняются на диске. После прерывания можно посмотреть причину, продолжить запуск через `/resume` или начать ту же задачу заново через `/retry`. Уже записанные изменения остаются в проекте.

Главный экран устроен как диалог с вводом снизу. Результаты проверок, изменения и расход токенов доступны отдельно. Статус `unverified` означает, что подтверждений работоспособности недостаточно; внешняя приёмка проекта остаётся отдельной задачей.

Это инструмент, который выполняет команды с правами локального пользователя. Ограничения путей и операций действуют на уровне приложения и не заменяют песочницу ОС. Ниже описаны запуск, подтверждения команд и значение каждого результата.

Обсудить похожий проект: [sh3l.beer](https://sh3l.beer).

## Установка

Нужны Python 3.12+, Linux и доступный в `PATH` авторизованный Codex CLI. Atlant использует установленный Codex CLI для вызовов модели; установка Python-пакета не устанавливает и не авторизует его.

Из каталога этого репозитория:

```sh
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install .
atlant --help
```

Для разработки: `python -m pip install -e '.[test]'`. `python -m pip install -r requirements.txt` устанавливает этот же пакет и зависимости из `pyproject.toml`. Команду `atlant` после установки можно запускать из любого каталога; инструкции моделей включены в пакет.

## Запуск

```sh
mkdir -p /path/to/project
atlant /path/to/project
```

Без аргумента используется текущий каталог. Режим **Агент** предназначен для изменения существующего проекта с учётом его кода; **Генерация** — для создания проекта по заданию. Введите задачу и нажмите `Enter` (также работает `Ctrl+Enter`). `Alt+Enter` добавляет новую строку. Режим меняется командами `/mode agent` и `/mode generate`. Во время работы новое сообщение уточняет текущую задачу. Изменения применяются непосредственно в выбранном каталоге.

Можно сразу передать задание:

```sh
atlant /path/to/project --mode agent --task 'Исправь обработку пустого ответа и проверь регрессию'
atlant /path/to/project --mode generate --task 'Создай приложение по следующему заданию: ...'
```

`Esc`, `Ctrl+C` или `/stop` останавливают агента, включая текущий вызов модели и запущенную проверку. Работает и прежнее сочетание `Ctrl+S`. Уже применённые изменения сохраняются. `Ctrl+Q` закрывает только интерфейс. Для повторного подключения используйте `/runs`, затем `/attach номер` или `/attach ID`; также можно указать ID при запуске:

```sh
atlant /path/to/project --attach RUN_ID
```

Сервис и процессы работы отделены от UI: закрытие терминального интерфейса не является остановкой. Это не системная служба с автозапуском: перезагрузка, завершение пользовательской сессии или внешнее убийство процессов могут прервать работу. Состояние сохраняется на диск, но незавершённая внешняя команда после прерывания требует проверки. Возобновление запуска выполняется командой `/resume`; простое подключение его не возобновляет.

## Работа без интерфейса

```sh
atlant /path/to/project --headless --mode agent --task 'Исправь ошибку и выполни проверки'
atlant /path/to/project --headless --attach RUN_ID
```

Headless выводит события и итоговый статус. Код завершения `0` означает `completed`; `1` — `failed`, `stopped`, `interrupted`, `unverified` или ошибку подключения. Код `2` означает ожидание подтверждения либо ошибочные аргументы CLI. При ожидании подтверждения запуск остаётся доступным через UI, команда подключения печатается в stderr. `Ctrl+C` отключает наблюдение с кодом `130`, сохраняя независимую работу сервиса.

Закрытие обычного UI с кодом `0` означает только успешное завершение интерфейса. Статус проекта виден под вводом и в итоговом сообщении; также доступен headless.

`/help` показывает команды. `/diff`, `/checks`, `/agents` и `/usage` выводят подробности в ленту только по запросу. `/new` начинает новую беседу после завершения или остановки запуска. После завершения можно сразу написать следующую задачу. Запрос разрешения автоматически переводит фокус на текстовый выбор: `↑`/`↓` выбирают действие, `Enter` подтверждает. Изначально выбран отказ, чтобы случайный Enter не запускал команду. `Tab` переключает выбор и поле ввода, сохраняя черновик. Также работают `/allow` и `/deny`. `PgUp`/`PgDn` листают историю прямо из ввода, `Ctrl+L` возвращает фокус во ввод. Клики для управления не нужны.

Над вводом — текущее состояние, действие и время его выполнения. Во время работы виден реальный план: выполненные шаги отмечены `✓`, текущий выделен; `/plan` показывает план целиком. Под вводом — короткое имя проекта, модель, режим и доступный расход токенов, затем подсказки клавиш. Подробный расход и кэш доступны через `/usage`. `Shift+Tab` переключает режим следующего запуска; опрос завершённого запуска не сбрасывает выбор.

Итог содержит изменённые файлы, результат проверок и объяснение завершения. При прерывании показывается записанная причина или явно сообщается, что она неизвестна. `/details` показывает причину, `/resume` продолжает сохранённый запуск, `/retry` начинает ту же задачу заново. Уже применённые изменения остаются в проекте.

## Настройки и данные

Настройки передаются через окружение. `.env.example` — справочник; CLI не загружает `.env` из рабочего проекта автоматически.

```sh
export CODEX_GATEWAY_MODEL=gpt-5.6-sol
export ATLANT_WORKERS=6
atlant /path/to/project
```

Новый локальный сервис наследует окружение при запуске. Подключение к уже работающему сервису сохраняет его прежние настройки. Модель должна быть доступна авторизованному Codex CLI. Сервис сам создаёт приватный токен для связи с UI и шлюзом; вручную задавать токен для обычного запуска `atlant` не требуется.

По умолчанию служебные файлы лежат в `${XDG_STATE_HOME:-~/.local/state}/atlant/<workspace-id>/`: `service.json`, журналы и каталог `runs/` с состояниями, событиями и контрольными точками. `ATLANT_STATE_DIR` меняет базовый каталог; он должен находиться вне целевого workspace. `service.json` содержит секрет доступа, журналы и состояния могут содержать текст задания и код: не публикуйте этот каталог.

Правила генерации встроены: Ponytail и до четырёх подходящих роли/задаче правил из десяти популярных coding-skills. Каталог, первоисточники, лицензии и дата наблюдения популярности находятся в [`models/prompt_rules.json`](atlant_coder/models/prompt_rules.json). Это компактные авторские адаптации; навыки не скачиваются и не запускаются как внешние команды. Обычный запуск использует `full` (или `ATLANT_POLICY_MODE` из окружения); API сохраняет выбранный `policy_mode=full|lite|off` отдельно для каждого запуска. Прямой запуск через `main.py` также поддерживает `ATLANT_POLICY_MODE`. Режим `off` отключает дополнительный текст, сохраняя проверки контрактов и протокола в коде.

В `full` чистый черновик не отправляется на безусловную повторную модельную самопроверку. Если автор указал проблемы, самопроверка остаётся; проверка формата ответа, границ разрешённых изменений, контрактов и результата проекта выполняется независимо. В `off` сохраняется прежний дополнительный review Python-черновиков для сравнения расходов.

Инструменты READ/LIST/SEARCH/PATCH/RUN ограничивают разрешённые операции и пути на уровне приложения. Это **не песочница ОС**: запускаемая команда исполняется с правами пользователя. Необычная команда требует подтверждения; обычные проектные проверки могут запускаться автоматически. Выбирайте workspace и разрешайте команды с учётом этих прав.

## Что означает результат

Корректность формата ответа, качество архитектуры и работоспособность результата проверяются отдельно:

- JSON Schema и протокол проверяют форму ответа и допустимые команды. Валидный JSON не доказывает правильность программы.
- CORE проверяет покрытие требований и согласованность интерфейсов до запуска файлов. Исправления первоначального плана учитываются отдельно от переработок уже утверждённой архитектуры.
- Проверки проекта, форматирование и ограниченные локальные исправления дают собственные результаты. `unverified` означает отсутствие достаточного подтверждения работоспособности; его нельзя считать PASS.
- Отсутствие архитектурных переработок само по себе не доказывает успех. Стиль, UX и соответствие визуальному заданию требуют своих критериев приёмки.

Счётчики начальных коррекций плана, архитектурных переработок, самопроверок черновиков и исправлений после тестов доступны отдельно. Native Codex сообщает накопительный расход по thread; шлюз переводит его в расход конкретного вызова, и Atlant суммирует эти значения. Если исходные данные отсутствуют или накопительный счётчик нельзя надёжно сравнить с предыдущим, расход показывается как неизвестный, а не как нулевой. Внешняя приёмка конкретного задания остаётся отдельной от внутренних проверок Atlant.

## Совместимость и проверка разработки

`python -m atlant_coder` эквивалентен `atlant`. В исходном репозитории сохраняется прежний вход `python main.py --home /path/to/project` для пакетного сценария: задание читается из `/path/to/project/task.atl`.

```sh
python -B -m pytest -q -p no:cacheprovider
python -m pip wheel . --no-deps --wheel-dir /tmp/atlant-wheel
```

Каталог `tests/` содержит единый набор тестов Атланта и шлюза. `task/` — отдельное сгенерированное приложение; оно не входит в пакет и тестовый набор Атланта.

Все команды моделей проходят через хендлеры SDK. `MAKE` начинает файловую задачу, `REQUEST` отправляет очередной запрос, `MADE` возвращает результат. `atlant_coder.app.run` — общий вход для фонового worker и пакетного запуска. Уточняющие раунды CORE отключены по умолчанию; `ATLANT_ASK_LOOPS` включает их явно.
